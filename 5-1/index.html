    MODULE 5 | OPERATE

    OPERATING IBM i WITH NATURAL LANGUAGE

    i. From modernization to operations

    In the previous modules, you used IBM Bob to transform a fixed-format OPM RPG program into free-format ILE RPG and to extend a new business field end to end across DDS, logical files, RPG and the display file. You then tuned the application's most expensive query and put its first unit tests in place. These are development-time activities: they change the application itself.

    Modernization is not complete when the last program compiles. The LPAR that runs the application needs attention too, and the same IBM i developer who just modernized the code is often the one asked to investigate a job that is consuming CPU, identify programs that have not been recompiled in years or answer a quick "is anything wrong?" question about the system.

    These operational tasks traditionally require memorizing CL commands (WRKACTJOB, DSPPGM, DSPJOB) or writing SQL against the QSYS2 system services. With IBM Bob, you can ask the same questions in plain English and get structured answers you can act on, using the same IDE and the same IBM i Developer mode you have used throughout the lab.

    Throughout this module, you will use IBM Bob to query active jobs and CPU consumption, optionally investigate a specific job in depth, and identify the stale programs in FLGHT400 that have not been recompiled in years.

    ii. Why this matters

    Day-to-day IBM i operations require quick, accurate answers to system-level questions.

    Getting those answers traditionally requires engineers to:

    • Know the right CL command or QSYS2 table function for each question
    • Interpret the difference between cumulative CPU time and elapsed CPU percentage
    • Navigate job logs, IFS process information and spool files manually
    • Cross-reference program compile timestamps against OS release levels
    • Distinguish facts from inferences when triaging a job
    TASK WITH: Manual Operations WITH: IBM Bob Premium Package for i
    Finding the jobs that consume CPU WRKACTJOB, sorted and read by eye A ranked table from QSYS2.ACTIVE_JOB_INFO, with cumulative and elapsed figures labelled
    Investigating one job DSPJOB, the job log and a PASE shell, cross-referenced by hand An investigation report that separates what was measured from what was inferred
    Building a modernization backlog DSPOBJD output exported to a spreadsheet A grouped list from QSYS2.OBJECT_STATISTICS, with notable findings called out

    Each of these tasks becomes a natural-language prompt, and the time saved is only part of the benefit. Bob structures the output into tables, explains what each column means and distinguishes facts from inferences, producing a clear report that an experienced operator would otherwise assemble by hand.

    iii. Querying your IBM i with Bob

    With IBM i Developer mode active and your FLGHT400 library on the library list, you will ask Bob three questions about your LPAR, each of a different kind.

    Using natural-language prompts in IBM i Developer mode, Bob can:

    • Query QSYS2.ACTIVE_JOB_INFO and other system services using SQL it writes on the fly
    • Present job data in structured tables with explanations of each column
    • Distinguish cumulative CPU time from real-time elapsed CPU percentage
    • Investigate a specific job's log, IFS process information and open files
    • Query QSYS2.OBJECT_STATISTICS to identify stale programs by compile date
    • Group findings by compiler version and OS release level

    ATTENTION: NON-DETERMINISTIC WORK AHEAD

    Bob's responses are non-deterministic, so the exact SQL queries, table layouts and analysis text you see may differ from those shown here.

    All this is to say: Your results ahead may vary. The key takeaway is that you understand how to ask Bob operational questions in plain English and interpret the structured output it returns. The exact job names, CPU figures and program lists will reflect the live state of your LPAR at the time you run the prompts.

    Prompt 1: Active jobs and CPU consumption

    The first question gives you a quick health check on your LPAR: which jobs are consuming the most CPU, and whether that consumption is cumulative (over the job's lifetime) or happening right now.

    1. In the Bob chat panel, click the + button (top-right) and choose New task in Library List to start a fresh task scoped to your library list. Confirm that IBM i Developer is the active mode.

    1. Copy and paste the following into the Bob chat prompt:

      Which active jobs have accumulated the most CPU time? For the top jobs, distinguish cumulative CPU time from their current elapsed CPU percentage.

      With the prompt entered, hit Enter or press the Send button to the right of the chat interface.

    1. Bob queries QSYS2.ACTIVE_JOB_INFO and returns a ranked table of active jobs showing job name, type, subsystem, user, function, CPU time (cumulative, in seconds) and elapsed CPU percentage (a real-time snapshot).

      Review the Key Observations section that follows the table. Bob explains:

      • Total CPU (sec) — the cumulative milliseconds of CPU consumed since the job started, converted to seconds
      • Elapsed CPU % — the job's share of CPU consumed during the last elapsed-time window, a real-time snapshot
      • An Analysis identifying which jobs dominate (typically the HTTP Server and JVM jobs, QBRMS backup recovery, QTCP mail server threads and system jobs) and whether any of them are currently CPU-bound

    Prompt 2 (optional): Investigate the top job

    The first prompt identified the jobs consuming CPU. This optional follow-up investigates the top-ranked job: its log, a fresh elapsed CPU measurement and its IFS process information.

    1. Copy and paste the following into the Bob chat prompt:

      Inspect the job ranked first and determine whether it is currently CPU-bound. Check its job log and take one fresh elapsed CPU measurement. If the log is empty and the job is a PASE process, inspect its IFS job information for its executable, working directory, and open application or log files. Stop after that investigation. Distinguish facts from inferences and provide no more than two recommendations.

      With the prompt entered, hit Enter or press the Send button.

    1. Bob produces a structured Investigation Report for the top job. Review the sections:

      • Fresh Elapsed CPU Measurement (fact): A table showing ELAPSED_CPU_PERCENTAGE, ELAPSED_CPU_TIME, CPU_TIME (cumulative lifetime), job status and disk I/O, followed by a verdict on whether the job is currently CPU-bound
      • Job Log (fact): A table of log messages with timestamps, message IDs and text, or a note that the log is empty
      • IFS Process Information (fact and inference): The executable path, PASE PID, PASE user, JVM version, working directory and open file handles, followed by Bob's inference about the application's identity based on the combination of subsystem, user profile, function tag and IFS path

    1. Scroll down to the Summary and Two Recommendations at the bottom of the investigation report.

      Bob separates facts (what it measured and read from the system) from inferences (what it concluded from those facts), and provides no more than two recommendations: for example, reviewing recent Navigator error logs or mounting /proc for open-file visibility.

    Prompt 3: Stale programs

    The final question concerns the modernization backlog: which programs in the FLGHT400 library have not been recompiled in the last five years. The answer says a good deal about the state of the codebase.

    1. Copy and paste the following into the Bob chat prompt:

      Which programs in the FLGHT400 library have not been recompiled in the last 5 years?

      With the prompt entered, hit Enter or press the Send button.

    1. Bob queries QSYS2.OBJECT_STATISTICS, filtering on object type *PGM in FLGHT400, compares the compile timestamps against the current date and returns the results grouped by compiler era.

      Review Group 1 — Original 1997 Compile. These are OPM RPG/400 and CLP programs compiled on OS/400 V3R2M0, roughly 29 years ago. The table shows program name, type (RPG or CLP), description, source member and compiler version.

    1. Scroll down to Group 2 — 2003–2004 Compile. These are programs recompiled during an OS upgrade cycle (V5R1M0 to V5R2M0), roughly 22 years ago. This group includes DFU programs, CLP utilities and some RPG programs that were touched during that migration and have not been recompiled since.

    1. Scroll down to the Notable Findings section. In the documented run, Bob highlighted:

      • All 33 programs listed are OPM (RPG/400 or CLP); there are no ILE programs (*MODULE or *SRVPGM) and no free-format RPGLE among them
      • The newest compile is from January 2004, over 20 years ago. Every program in the list is stale by the five-year threshold
      • AGENTDFU has no source member; it was generated by DFU and cannot be conventionally recompiled without regeneration
      • The 1997 programs used compiler 5763RG1 (RPG/400 for V3R2M0), nine OS releases behind the current IBM i 7.6

      Your own list will differ in one respect: FRS409 and FRS021 now carry today's compile date, because you rebuilt them in Module 2. The remaining programs are the modernization backlog.

    iv. Key takeaways

    • IBM Bob can answer system-level operational questions in plain English, with no need to memorize CL commands or QSYS2 table function syntax
    • Bob queries the right system services on its own (QSYS2.ACTIVE_JOB_INFO, QSYS2.OBJECT_STATISTICS, job logs and IFS process information) and presents the results in structured, readable tables
    • The distinction between cumulative CPU time and elapsed CPU percentage matters for job triage. Bob explains and labels both, which prevents the common mistake of treating a high lifetime CPU total as evidence of a current problem
    • When investigating a specific job, Bob separates facts (what it measured and read from the system) from inferences (what it concluded from those facts)
    • The stale-program query produces a modernization backlog, grouped by compiler era, with notable findings that identify programs with no source, programs compiled on obsolete OS releases and the absence of any ILE or free-format programs
    • These operational prompts work in the same IBM i Developer mode and the same IDE session you used for analysis, modernization, tuning and testing. You do not switch modes or tools, and the task context carries over
    • Human review remains essential. Bob's analysis reflects the system state at the moment you run the prompt, so verify its findings against your own knowledge of the environment before acting on them
