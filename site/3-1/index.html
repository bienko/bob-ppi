    MODULE 3 | OPTIMIZE

    REVIEWING AND TUNING DB2 FOR i SQL

    i. From source code to the database beneath it

    In the previous Modernize module, you used IBM Bob to convert a fixed-format OPM RPG program into free-format ILE and to extend a new business field end to end across DDS, logical files, RPG and a display file. Both are changes to the application's source. The database those programs use needs the same attention, and on IBM i that work is done in SQL.

    FLIGHT400's files were defined in DDS in the 1990s, but the reports and integrations written against them today are SQL. They join FLIGHTS, ORDERS, AGENTS and CUSTOMERS, aggregate by flight and filter by date. Those statements are written by developers who may never have seen the DDS, against column names such as FLIGH00001 that the system generated from the original field names. A statement that is logically wrong on a strict SQL engine, or that forces Db2 for i to scan the largest file in the application for every request, is easy to write, and a reviewer can miss it.

    Throughout this module, you will switch Bob into IBM i Database mode and use it in two ways. First you will review a query handed to you by a junior developer with the /review slash command, which checks the statement against the live catalog and reports what it finds. Then you will run the SQL Index Strategy Advisor workflow, which captures performance data from the plan cache, reads the Index Advisor's recommendations and proposes a permanent index for the query.

    ii. Why this matters

    Database performance on IBM i depends on access paths, and few people understand the optimizer well enough to choose them.

    Reviewing and tuning a Db2 for i statement by hand requires practitioners to:

    • Map system-generated column names back to the business fields they represent
    • Spot statements that are logically incorrect even when they happen to run
    • Read Visual Explain output and plan cache snapshots to find the table and predicate that dominate the cost
    • Interpret the Index Advisor's recommendations and the maintained temporary indexes (MTIs) the system has already built on its own
    • Choose an index that helps the workload without burdening every insert and update
    TASK WITH: Manual Tuning WITH: IBM Bob Premium Package for i
    Query review A senior DBA's time, when one is available /review checks correctness, security and performance against the live catalog in one pass
    Finding the bottleneck Visual Explain and plan cache dumps read by hand A plain-language answer to "which table is the bottleneck and why?"
    Choosing an index Index Advisor rows interpreted by an expert A guided workflow that turns plan cache evidence into CREATE INDEX statements you approve
    Keeping the knowledge Held by the DBA alone A workflow summary that records the data source, the findings and the indexes created

    iii. Optimizing FLIGHT400 queries with IBM Bob

    The work in this module runs in IBM i Database mode, the second of the two modes the Premium Package contributes. Where IBM i Developer is built around source members and compiles, IBM i Database is built around Db2 for i. It generates, modernizes, tunes and reviews SQL, and it carries the catalog skills and the index-advisory workflow you are about to use.

    Using IBM i Database mode, Bob can:

    • Review a SQL statement for correctness, security, performance and style, verifying names and data types against the connected system's catalog
    • Explain which table and which predicate dominate a statement's cost
    • Capture performance data from the SQL plan cache into a database monitor file
    • Read the Index Advisor's recommendations and the system's temporary index activity
    • Generate CREATE INDEX statements, explain the expected benefit of each and create the ones you approve
    ATTENTION: NON-DETERMINISTIC WORK AHEAD

    Bob's responses are non-deterministic, and the optimizer's advice depends on the statements that have run on your partition. The findings from /review, the bottleneck explanation and the index recommendations you see may differ from those shown here, in wording and in detail.

    All this is to say: Your results ahead may vary. The key takeaway is that you understand how to review a statement with the slash command, how to run the SQL Index Strategy Advisor workflow and how to read what it recommends. Expect the highest-priority recommendation to involve ORDERS and its date column; the exact column order and index name may differ.

    iv. Reviewing a query with /review

    The statement below was written to report ticket sales by flight and agent for a three-day window in February 2004. It joins four files, aggregates by class of service and has been handed to you for review before it goes into a report. It contains at least one logical fault.

    1. In the Bob chat panel, click the mode selector at the bottom and choose IBM i Database.

      • Click + › New task in Library List to start a clean task scoped to QGPL, QTEMP and FLGHT400
      • Confirm in the Permissions menu that Documentation and Understand are enabled

    1. Type /review into the prompt field. The command list above the field narrows to the SQL review command, described as "Review a Db2 for i SQL statement for simplification, optimization, security…".

      Select it so that /review is highlighted as a command chip in the prompt.

      THE COMMAND NAME MAY DIFFER BY RELEASE

      In the documented run the command appeared as /review. Later releases of the Premium Package list it as /review_SQL, alongside a /review_rpg counterpart for RPG source. Either way, type /review and pick the SQL entry from the list; typing the whole command without selecting it from the list leaves it as plain text, and Bob will treat the query as a question rather than a review.

    1. With the command highlighted, paste the following query after it and send the prompt. The pasted statement appears as a Pasted text chip beside the command.

      SELECT
    f.FLIGH00001                                    AS FLIGHT_NUMBER,
    f.DEPARTURE                                     AS FROM_CITY,
    f.ARRIVAL                                       AS TO_CITY,
    f.AIRLINES                                      AS AIRLINE,
    f.DAY_O00001                                    AS DAY_OF_WEEK,
    f.DEPAR00002                                    AS DEPARTURE_TIME,
    f.ARRIV00002                                    AS ARRIVAL_TIME,
    f.MILEAGE,
    f.TICKE00001                                    AS TICKET_PRICE,
    f.SEATS00001                                    AS SEATS_AVAILABLE,
    ag.AGENT_NAME,
    COUNT(DISTINCT o.CUSTO00001)                    AS UNIQUE_CUSTOMERS,
    SUM(o.TICKE00001)                               AS TOTAL_TICKETS_SOLD,
    SUM(CASE WHEN o.CLASS = 'F' THEN o.TICKE00001 ELSE 0 END) AS FIRST_CLASS_TICKETS,
    SUM(CASE WHEN o.CLASS = 'B' THEN o.TICKE00001 ELSE 0 END) AS BUSINESS_TICKETS,
    SUM(CASE WHEN o.CLASS = 'E' THEN o.TICKE00001 ELSE 0 END) AS ECONOMY_TICKETS,
    MIN(o.DEPAR00001)                               AS EARLIEST_BOOKING_DATE,
    MAX(o.DEPAR00001)                               AS LATEST_BOOKING_DATE
FROM FLGHT400/FLIGHTS       f
JOIN FLGHT400/ORDERS        o  ON o.FLIGH00001  = f.FLIGH00001
JOIN FLGHT400/AGENTS        ag ON ag.AGENT_NO   = o.AGENT_NO
LEFT JOIN FLGHT400/CUSTOMERS c  ON c.CUSTO00001  = o.CUSTO00001
WHERE o.DEPAR00001 >= TIMESTAMP('2004-02-08-00.00.00')
  AND o.DEPAR00001 <  TIMESTAMP('2004-02-11-00.00.00')
GROUP BY
    f.FLIGH00001, f.DEPARTURE, f.ARRIVAL, f.AIRLINES,
    f.DAY_O00001, f.DEPAR00002, f.ARRIV00002,
    f.MILEAGE, f.TICKE00001, f.SEATS00001, ag.AGENT_NAME
ORDER BY
    o.DEPAR00001,
    f.FLIGH00001
FETCH FIRST 100 ROWS ONLY;

      THE FAULT TO LOOK FOR

      o.DEPAR00001 appears in the ORDER BY clause but not in the GROUP BY clause. Ordering an aggregated result by a column that is neither grouped nor aggregated is logically incorrect, and strict SQL engines reject it with SQL0122. Read the review with that in mind and check whether Bob catches it on its own.

    1. Bob reviews the statement. It may inspect the connected system's catalog to verify the column names and data types, so approve the tool requests as they appear. In the documented run, the findings included:

      • ❌ ORDER BY o.DEPAR00001 uses a column that is neither grouped nor aggregated and may fail with SQL0122; Bob proposed replacing it with MIN(o.DEPAR00001)
      • ⚠️ The LEFT JOIN to CUSTOMERS contributes no columns to the result and can be removed
      • ⚠️ o.DEPAR00001 is the order's DEPARTURE_DATE, so the EARLIEST_BOOKING_DATE and LATEST_BOOKING_DATE aliases are misleading
      • ⚠️ TICKET_PRICE is stored as VARCHAR(22) and requires validation before it is used in numeric calculations
      • ✅ The CASE-based class-of-service breakdown is a clear, set-based approach
      • ✅ FETCH FIRST 100 ROWS ONLY is a useful safeguard while testing
      • 💡 Bob recommended descriptive SQL column names in place of the generated IBM i system names

      The last point has consequences beyond this one statement. FLIGH00001 is the system name Db2 for i generated for a field whose DDS name was longer than ten characters; the same column also carries an SQL name (FLIGHT_NUMBER) that matches the business name of the field. Bob's corrected statement uses the SQL names, which is why the index recommendations later in this module name DEPARTURE_DATE and FLIGHT_NUMBER rather than DEPAR00001 and FLIGH00001.

    1. The Index Advisor records advice only for statements that the optimizer has processed, and the query above has not yet been executed.

      Ask Bob to apply its corrections and execute the result. Within the Agentic Sidebar chat, copy & paste the following instruction. Press Enter to execute the task.

      Apply the corrections you recommended and run the corrected statement against FLGHT400, keeping FETCH FIRST 100 ROWS ONLY. Show me the first few rows of the result and confirm that the statement ran without error.

      Bob rewrites the statement, runs it through its SQL tool and returns the first rows. Approve the tool request when it appears. The run takes a few seconds; it also leaves an entry in the SQL plan cache, which is what the workflow in the next section analyzes.

    1. With the statement in context, ask the question a DBA would ask next. Within the Agentic Sidebar chat, copy & paste the following instruction. Press Enter to execute the task.

      Is any table a performance bottleneck in this query, and why?

      In the documented run, Bob identified four things:

      • ORDERS is the largest file in the join
      • The query filters it on DEPARTURE_DATE
      • Only a small fraction of its rows qualify for the three-day window
      • The date-range predicate is therefore highly selective and a strong candidate for index optimization

      The answer is informational and will vary with the optimizer's statistics on your partition. Its value is in naming the file and the predicate that an index would help.

    v. Running the SQL Index Strategy Advisor workflow

    Db2 for i records the indexes it would benefit from. Every time the optimizer processes a statement, it notes in the Index Advisor the access paths that would have made the statement cheaper, and when the benefit is large enough it builds a maintained temporary index (MTI) on its own.

    The SQL Index Strategy Advisor workflow collects that evidence from the plan cache, analyzes it and proposes permanent indexes, which you approve one at a time before Bob creates them.

    WHAT THE CAPTURE DOES

    The workflow's Capture New Performance Data option calls the DUMP_PLAN_CACHE_TOPN procedure, which writes the top N statements from the SQL plan cache (ranked by the category you choose) into a database monitor file in an output library. The analysis then runs against that file: the Index Advisor recommendations, the MTI activity and the query statistics for each captured statement. Nothing is created until you approve it.

    1. Still in IBM i Database mode, click the workflow icon (the play button at the top-right of the Bob panel) and choose Run Workflow in Library List.

      In the workflow catalog, click Start on SQL Index Strategy Advisor, then Get Started.

    1. The workflow asks for its data source and capture settings. Use the following values and continue through each prompt:

      SETTING VALUE
      Data Source Capture New Performance Data
      Capture Method DUMP_PLAN_CACHE_TOPN
      Output Library FLGHT400
      Output Object Name FLGHT400P
      Top N Queries 20
      Top N Category Runtime

      EXPLAINING THESE VALUES

      The output library and object name decide where the monitor file lands; keeping it in FLGHT400 keeps the lab's objects together. Runtime ranks the plan cache by the statements that have consumed the most time, which is where the ticket sales query sits after its run. Twenty statements is enough to cover everything Bob has executed in this lab without burying the one this module is about.

    1. Bob captures the performance data and works through the analysis, pausing for tool approvals along the way. The documented run performed the following steps; yours may group them differently:

      • Captured the top 20 statements from the plan cache into FLGHT400/FLGHT400P
      • Examined the plan cache information for each statement
      • Reviewed the Index Advisor's recommendations
      • Examined the temporary index (MTI) activity
      • Identified candidate permanent indexes
      • Generated CREATE INDEX statements
      • Explained the expected performance benefit of each index

    1. Review the recommendations. In the documented run, the highest-priority candidate was an index on ORDERS keyed by the date and flight columns that the ticket sales query filters and joins on:

      CREATE INDEX FLGHT400.ORDERS_IDX_DEPDT_FLT
    ON FLGHT400.ORDERS (
        DEPARTURE_DATE,
        FLIGHT_NUMBER
    );

      A second candidate, keyed on the agent and the date, may appear alongside it:

      CREATE INDEX FLGHT400.ORDERS_IDX_AGT_DEP
    ON FLGHT400.ORDERS (
        AGENT_NO,
        DEPARTURE_DATE
    );

      The first directly supports the selective date-range predicate, with the flight number available for the join, and is the one to create. Leave the others as documented recommendations.

      CREATE ONE INDEX AT A TIME

      An index speeds up the statements that use it and adds cost to every insert, update and delete on the file it covers. The advisor's list is a set of candidates ranked by evidence from the capture, so approve the one with the clearest benefit and leave the rest as documentation. On a shared partition the same caution applies to scope: create indexes only in your own library.

    1. When Bob asks which recommendations to apply, respond with the following prompt (or select the equivalent option in the workflow):

      Apply the highest-priority index only, in FLGHT400.

      Bob runs the CREATE INDEX statement and reports success. The workflow closes with a summary covering the data source, the findings, the index created and the recommended next steps.

    1. Confirm the result from the catalog:

      List the indexes that exist on FLGHT400/ORDERS, with their key columns.

      The new index appears among the keyed access paths over ORDERS. In the Object Browser, refresh the FLGHT400 filter: an SQL index is an IBM i file object with the logical-file attribute, so ORDERS_IDX_DEPDT_FLT is listed alongside the application's own logical files. Run the corrected ticket sales query once more and the optimizer will pick the new access path for the date range.

    vi. Key takeaways

    • IBM i Database mode gives Bob the Db2 for i skills, the catalog tools and the index-advisory workflow; switch to it whenever the subject is SQL rather than source members
    • /review checks a statement against the live catalog and reports correctness, security, performance and style findings in one pass. Select the command from the list so that it is highlighted; as plain text it has no effect
    • A statement that runs may still be wrong. Strict SQL engines reject an ORDER BY on a non-grouped column, while lenient ones accept it without warning
    • Prefer the SQL names of columns (DEPARTURE_DATE, FLIGHT_NUMBER) over the generated system names (DEPAR00001, FLIGH00001). Both reach the same column, and the SQL name is the meaningful one
    • The optimizer records index advice for the statements it runs, so a query must be executed at least once before the advisor has anything to say about it
    • The SQL Index Strategy Advisor workflow captures the plan cache with DUMP_PLAN_CACHE_TOPN, reads the Index Advisor recommendations and the MTI activity, and proposes permanent indexes that you approve individually
    • Create the index with the clearest benefit and leave the rest as documented candidates; every index adds cost to every insert, update and delete
    • Human review remains essential. The advisor's recommendations are based on captured evidence, but they are still only recommendations. The decision to add an access path to a production file belongs to the team that owns the file
