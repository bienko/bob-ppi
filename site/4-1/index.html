    MODULE 4 | TEST

    PLANNING AND IMPLEMENTING RPGUNIT TESTS

    i. From a tuned database to a tested codebase

    In the previous Optimize module, you reviewed a SQL statement with /review, ran it against FLGHT400 and let the SQL Index Strategy Advisor workflow turn plan cache evidence into a permanent index on ORDERS. The application is now better documented, partly modernized and faster on its most expensive query. It still has no automated tests.

    This is typical of an IBM i estate. The people who wrote these programs in 1997 tested them by hand on green screens, and much of what they knew about the expected behavior was never written down. Every change you made in Module 2 was verified by reading diffs and by looking at a 5250 screen, which is adequate for one change but impractical across dozens. A modernization program that expects to touch dozens of programs needs tests that run on their own.

    Throughout this module, you will create a small SQLRPGLE service module named CUSTCHK, then use the Premium Package's two RPGUnit workflows to test it. RPGUnit Test Plan Creation analyzes the module's exported procedures and writes a structured test plan as Markdown documents. RPGUnit Test Suite Implementation reads those documents, writes the test source members, runs the suites through the IBM i Testing extension and iterates until the tests pass.

    ii. Why this matters

    Automated tests make modernization repeatable. Most IBM i estates have none.

    Bringing unit tests to an RPG codebase by hand requires engineers to:

    • Learn the RPGUnit framework, its assertion procedures and its compile commands
    • Decide, for every exported procedure, which branches and boundary values deserve a test case
    • Write the test scaffolding (suites, set-up and tear-down, utilities) for each module before writing a single assertion
    • Compile the module and the suite, run them, read the results and iterate
    • Keep a written test plan that the next engineer can follow
    TASK WITH: Manual Testing WITH: IBM Bob Premium Package for i
    Test plan A document that is rarely written Template, module, test suite and utilities documents generated from the exported procedures
    Test boilerplate RPGUnit scaffolding written by hand for each procedure Test source members generated from the plan
    Running and iterating Compile, run, read the spool file, fix, repeat The suite runs through the IBM i Testing extension and Bob iterates until it passes
    Coverage of legacy code None A path to tests for programs that never had any

    iii. Testing FLIGHT400 with IBM Bob

    The two RPGUnit workflows work together in sequence. Both run in IBM i Developer mode with the library list as their workspace, and both depend on the IBM i Testing extension and the RPGUnit framework being present on the partition, which is where this module begins.

    Using IBM i Developer mode and the RPGUnit workflows, Bob can:

    • Install the RPGUnit framework on the partition through the connection's Components settings
    • Analyze a module's exported procedures and identify the branches and boundary values each one exposes
    • Write a test plan as Markdown documents in an IFS project directory
    • Generate RPGUnit test source members from the plan, together with a testing.json that the IBM i Testing extension reads
    • Run the suites, read the results and correct the tests (or point to a fault in the code under test) until they pass

    ATTENTION: NON-DETERMINISTIC WORK AHEAD

    Bob's responses are non-deterministic, so the number of test cases it plans, the names it gives them and the order in which the workflow prompts you may differ from those shown here.

    All this is to say: Your results ahead may vary. The key takeaway is that you understand how the two workflows divide the work (a plan first, then an implementation that runs until it passes) and how to read the result in the Test Results panel. Whether Bob writes four test cases or six for checkCustomerExists is of less importance than the fact that they run and pass.

    iv. Installing RPGUnit on the partition

    RPGUnit is an open-source unit testing framework for ILE RPG. The IBM i Testing extension knows how to install it on a connected partition as a component, and the Premium Package's workflows expect to find it there, in a library named RPGUNIT.

    1. Open the Extensions view (Cmd+Shift+X / Ctrl+Shift+X), search for IBM i Testing and confirm that the extension appears under Installed. It arrived with the IBM i Development Pack during Setup; if it is missing, click Install and reload when prompted.

    1. Open the settings for your connection. In the status bar at the bottom of the window, click the gear icon labelled with your connection name (IBM i Modernization) and choose the connection settings from the options presented. A Settings: IBM i Modernization tab opens in the editor area, with tabs for Mapepire, Features, Source Code, Terminals, Debugger, Temporary Data and Components.

      ANOTHER ROUTE TO THE SAME PAGE

      The same settings open from the IBM i sidebar: right-click the connection and choose its settings.

    1. Click the Components tab. It lists the components that the installed extensions contribute and whether each is present on the partition. Code for IBM i contributes mapepire (installed, required). IBM i Testing contributes RPGUnit, shown as NotInstalled (optional), and CODECOV (installed, required).

      Click Install component.

    1. In the Install component picker, tick RPGUnit and click OK. The extension creates the RPGUNIT library on the partition and installs the framework's service program and commands into it. When the Components tab reports RPGUnit as Installed, click Save settings and close the tab.

    1. Add the two testing libraries to your library list, the same way you added FLGHT400 during Setup. In the IBM i sidebar, hover over User Library List, click the + (Add library) icon, type RPGUNIT and press Enter. Repeat for QDEVTOOLS.

      Your list should now read QGPL, QTEMP, FLGHT400, RPGUNIT and QDEVTOOLS.

      WHAT THE TWO LIBRARIES HOLD

      RPGUNIT holds the framework: the assertion procedures that your tests call and the commands that compile and run a suite. QDEVTOOLS is the IBM-supplied library that the extension's code-coverage component draws on. The suites compile with both on the library list, which is why the workflows check for them and offer to add them if they are missing.

    v. Creating the CUSTCHK source member

    The subject of the tests is a service module small enough to understand in one reading. CUSTCHK exports a single procedure, checkCustomerExists. It takes a customer number and returns an indicator saying whether that customer exists in CUSTOMRZ (the renamed logical view over the CUSTOMERS file).

    1. In the Object Browser, expand the FLGHT400 filter and right-click the qrpglesrc source file. Choose New Member….

    1. When prompted for the member name, enter CUSTCHK.SQLRPGLE and confirm. If the extension asks for a description, enter Customer existence check. The new, empty member opens in the editor.

    1. Paste the following source into the member and save it with Cmd+S / Ctrl+S:

      **free
ctl-opt nomain;

dcl-proc checkCustomerExists export;
  dcl-pi *n ind;
    custId packed(9:0) const;
  end-pi;

  dcl-s rowCount int(10);

  exec sql
    select count(*)
      into :rowCount
      from CUSTOMRZ
      where CUSTNO = :custId;

  return (SQLCODE = 0 and rowCount > 0);
end-proc;

      WHY A NOMAIN MODULE

      RPGUnit tests exported procedures, and a NOMAIN module with one exported procedure is the smallest unit it can exercise. The procedure gives a test plan three things to work with: a boundary on its input (zero, negative and maximum customer numbers), two outcomes (found and not found) and an embedded SQL statement whose SQLCODE decides the result. The test suite Bob writes binds to this module and calls checkCustomerExists with each case.

    1. The test suite needs a compiled module to bind to. Ask Bob to build it. In the Bob chat panel, confirm that IBM i Developer is the active mode, click + › New task in Library List and send:

      Compile FLGHT400/QRPGLESRC/CUSTCHK.SQLRPGLE as an ILE module in FLGHT400 using CRTSQLRPGI with OBJTYPE(*MODULE), and confirm the result.

      Approve the tool request. Bob runs the compile and reports the module FLGHT400/CUSTCHK created. If you skip this step, the implementation workflow detects the missing module during its environment validation and offers to compile it for you.

    vi. Running the RPGUnit Test Plan Creation workflow

    The first workflow produces the plan. It runs any existing test suites to learn the current state of testing (there are none yet) and analyzes how the module's exported procedures are used. It then writes four kinds of Markdown document into an IFS project directory:

    • Template documents, the reusable blueprints
    • A module document for CUSTCHK that covers each exported API and its branches
    • A test suite document that lists the suites and cases to implement
    • A single test utilities document for shared helper procedures

    1. Click the workflow icon at the top-right of the Bob panel and choose Run Workflow in Library List. In the catalog, click Start on RPGUnit Test Plan Creation, then Get Started. When the workflow asks which library to plan for, select FLGHT400.

    1. When prompted for the IFS project directory, enter:

      /home/ITZUSER/flght400

      This is the directory that received the business-rules report in Module 1. The plan documents land in a subdirectory of it, and the implementation workflow reads them from the same place.

    1. Answer the workflow's remaining prompts as follows:

      • Tell Bob to create a new test plan (this is the first run)
      • Select the default recommended path for the goal
      • Let Bob locate testable files automatically. It scans the library and finds CUSTCHK.SQLRPGLE as the only suitable candidate
      • Select the exported procedure checkCustomerExists and proceed
      • Choose to validate the environment

      If the validation reports RPGUnit or QDEVTOOLS as missing, accept the offer to install the component and add the library to your library list; you completed both earlier, so in most runs the validation passes without prompting.

      IF BOB OFFERS TO START OVER

      If Bob asks at any point whether to run the RPGUnit Test Plan Creation workflow again, select No thanks. The offer appears when the workflow's own summary mentions test planning; a second run would regenerate the same documents.

    1. Bob writes the test plan documents and stores them in the IFS directory you specified. At the bottom of the chat panel, review the files it created. In the documented run, the module document listed five cases for checkCustomerExists: an existing customer, a customer that does not exist, a zero customer number, the maximum customer number and a negative customer number.

      Open the module document from the IFS Browser (/home/ITZUSER/flght400, then the plan subdirectory) and read it before moving on. It is the specification that the next workflow implements. If you want to add or remove a case, do it in this document before the next workflow writes the RPG.

    vii. Running the RPGUnit Test Suite Implementation workflow

    The second workflow turns the plan into running tests. It reads the documents, writes or updates the RPGUnit test suites and creates the testing.json that the IBM i Testing extension uses to run them. It then runs the suites and iterates until the new tests pass. If it finds pre-existing failures it flags them and asks whether to fix them.

    1. Click the workflow icon again, choose Run Workflow in Library List and click Start on RPGUnit Test Suite Implementation. The workflow notices that a test plan is already in place; click Proceed.

    1. Select FLGHT400 as the library, enter the same IFS project directory (/home/ITZUSER/flght400) and confirm the path to the test suites, which Bob pre-fills with the correct default.

      Choose to validate the environment. If Bob prompts to download RPGUnit again, click Install, then Cancel on the follow-up popup that asks to delete the existing version.

    1. Bob generates the test source member (CUSTCHKT.SQLRPGLE in the QTESTSRC source file, in the documented run) and compiles it through the IBM i Testing extension. It then runs the suite and iterates until the new tests pass or until it discovers an error in the code under test. Approve the tool requests as they appear.

      The Test Results panel at the bottom of the IDE reports the outcome. In the documented run:

      • Execution: 0 deployments; 1 compilation, successful
      • Results: 1 test file passed; 5 test cases passed, 0 failed, 0 errored; 5 assertions; PASS
      • The five cases: test_checkCustomerExists_exists, test_checkCustomerExists_notFound, test_checkCustomerExists_zeroId, test_checkCustomerExists_maxId and test_checkCustomerExists_negativeId

      The IBM i Testing view on the right lists the same cases with a check beside each, under the FLGHT400 library and the CUSTCHKT.SQLRPGLE suite.

    1. Open the generated suite from the Object Browser (FLGHT400 › qtestsrc › custchkt.sqlrpgle) and read it against the module document. Each test case sets up its input, calls checkCustomerExists and asserts the expected indicator with the RPGUnit assertion procedures. The workflow wrote this scaffolding from the module document.

      TROUBLESHOOTING: A TEST FAILS

      Ask Bob to explain the failure and help fix it: "Explain why test_checkCustomerExists_maxId failed and propose the smallest fix." The fault may be in the test's expectation, in the test data (a customer number that happens to exist in CUSTOMRZ) or in CUSTCHK itself. The workflow distinguishes new failures from pre-existing ones and asks before it changes the code under test.

    viii. Key takeaways

    • The Premium Package splits testing into two workflows: RPGUnit Test Plan Creation writes the plan as Markdown documents, and RPGUnit Test Suite Implementation turns the plan into test source, runs it and iterates until it passes
    • RPGUnit is installed on the partition as a component of the IBM i Testing extension, from the connection's Components settings, and lives in the RPGUNIT library; RPGUNIT and QDEVTOOLS must be on the library list for suites to compile
    • A NOMAIN module with an exported procedure is the smallest unit RPGUnit can exercise; the workflows find such procedures on their own and plan cases around their branches and boundaries
    • Review and adjust the cases in the plan documents before running the implementation workflow
    • The Test Results panel and the IBM i Testing view report the outcome of every run, and a failing case is the starting point for a follow-up prompt to Bob
    • Human review remains essential. The tests reflect Bob's reading of the procedure, so confirm that the cases cover what the business cares about before relying on the suite to guard later changes
