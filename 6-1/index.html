    MODULE 6 | EXTEND (OPTIONAL)

    GENERATING A REACT CARBON APP FROM A GREEN SCREEN

    i. From the green screen to the browser

    The five required modules are complete, and the accreditation instructions in Module 5 are where the course formally ends. This optional module is for the participant with time and token budget to spare, and it covers the one layer the earlier modules did not touch: the user interface.

    Every screen in FLIGHT400 is a 5250 display file. The Create Order screen (FRS001DF, driven by FRS001) is a good example: two boxed panels of flight and ticket information, a row of function keys along the bottom and a set of fields whose valid values live in lookup programs reached with F4 through F7. Its business logic is sound. Clients usually raise modernization because of the 5250 interface.

    Throughout this module, you will give Bob a helper skill that captures how to build and run a React and Vite application inside IBM i PASE, then switch to IBM i Developer mode and ask Bob to generate a single-page React application styled with IBM Carbon from a screenshot of the 5250 screen. Bob reads the display file and the RPG program behind it, scaffolds the project in the IFS, builds it on the partition and starts its development server there. You open the result in your own browser through an SSH tunnel.

    THIS MODULE IS OPTIONAL

    Expect about 30 minutes, most of it spent waiting for npm install to finish on the partition. The module installs Node.js in PASE if it is not already present, which is a change to the partition beyond the FLGHT400 library. Nothing here is required for accreditation.

    ii. Why this matters

    A modern front end is the most visible modernization outcome. On IBM i it is often handed to an outside team, because the toolchain is unfamiliar to RPG developers.

    Building a web front end for a 5250 transaction by hand requires practitioners to:

    • Read the display file DDS and the RPG program to learn which fields exist, which are input and which carry lookups
    • Know the quirks of running Node.js, npm and a bundler inside PASE on a big-endian POWER system
    • Choose and configure a design system so that the result looks like an enterprise application rather than a prototype
    • Keep the development server running in the background without tying up the session that started it
    • Reach the server from a developer's laptop through whatever network path the partition allows
    TASK WITH: Manual Development WITH: IBM Bob Premium Package for i

    PASE toolchain pitfalls Discovered one failed build at a time Recorded in a helper skill that Bob applies on each run
    Scaffolding and styling Hours of boilerplate and Carbon configuration A generated project with the theme, components and launch scripts in place
    Running on the partition Shell scripts written by hand Start and stop on request, with the server detached from the chat session

    iii. Extending FLIGHT400 with IBM Bob

    The work in this module combines three things you have already used (a skill, the IBM i Developer mode and Bob's IFS and PASE tools) with one you author yourself. The skill is the new element.

    React and Vite run well inside PASE, but only once a handful of platform-specific problems are solved. There are still issues with:

    • The native esbuild binary does not exist for os400
    • npm postinstall scripts hang
    • An interactive scaffolding prompt freezes the tool channel
    • nohup npm run dev & leaves a pipe open that cancels the call

    A skill records those solutions so that Bob applies them without being told.

    Using IBM i Developer mode with the helper skill in place, Bob can:

    • Read FRS001DF.DSPF for the screen layout and field names, and FRS001.RPG for the pricing logic and field definitions
    • Scaffold a React 18 and Vite 4 project in the IFS and install its dependencies with npm
    • Patch esbuild for os400 and configure Vite and Sass for the Carbon theme
    • Write the launch scripts and start the development server in the background on a port you choose
    • Stop the server again when you are done
    ATTENTION: NON-DETERMINISTIC WORK AHEAD

    Bob's responses are non-deterministic, and this module asks Bob to design a user interface, which leaves more room for variation than any earlier prompt. The layout, component choices and lookup values you see will differ from the screenshot, and the build may need a second attempt if a step of the skill is skipped.

    All this is to say: Your results ahead may vary. The key takeaway is that you understand how to capture platform knowledge in a skill, how Bob combines it with the Premium Package's own skills to read a 5250 screen, and how a generated application is built and run on the partition. Whether your page matches the one shown is of less importance than the fact that it renders the Create Order screen in a browser.

    iv. Preparing Node.js on the partition

    PREREQUISITES

    Before undertaking this module's tasks, confirm that the following is prepared:

    • The SSH private key from Setup is still in your local workspace folder, and an SSH client is available in the Bob IDE's integrated terminal
    • Port 3001 is free on your laptop (the tunnel binds it) and on the partition (the development server binds it)
    • The IBM i Modernization connection is active and FLGHT400 is on the library list

    The Certified PowerVS Base VM ships without Node.js. As with tn5250 during Setup, you will have Bob install it rather than doing so by hand. PASE packages come from yum, and the Node.js packages are versioned (nodejs20, nodejs22 and so on) rather than published under a generic name.

    1. Within the Agentic Sidebar chat, confirm that IBM i Developer is the active mode, click + › New task in Library List and send the following prompt:

      Check whether Node.js and npm are installed in PASE on this partition by running /QOpenSys/pkgs/bin/node --version and /QOpenSys/pkgs/bin/npm --version. If Node.js is missing, list the nodejs packages available from yum, install the newest version that is 18 or later (for example yum install nodejs22), and report both versions when done.

      Approve the PASE command requests as they appear. The install takes a few minutes and ends with Bob reporting a Node.js version of 18 or later and an npm version of 9 or later.

      WHY THE FULL PATH?

      PASE shells do not add /QOpenSys/pkgs/bin to the PATH automatically, so node on its own reports No such file or directory even when Node.js is installed. The helper skill you create next tells Bob to use the fully qualified path everywhere and to export the PATH at the top of every script it writes, which avoids a whole class of confusing failures.

    v. Creating the helper skill

    A skill is a Markdown file with a short frontmatter (a name and a description that tells Bob when to apply it) followed by the instructions themselves. You first encountered the Premium Package's own skills in Module 1, when understand-app-overview answered a question from the scan. In this module, you'll create it yourself. The text is provided with the lab; you will paste it into a chat and ask Bob to turn it into a skill.

    1. Open the skill text: ibmi-react-vite-SKILL.txt. Save it into your local workspace folder (~/ibmiflight400) or open it in the Bob IDE's editor, then select its entire content and copy it.

      WHAT THE SKILL ENCODES

      Read it before you paste it; it is a compact account of what goes wrong when a toolchain written for Linux runs in PASE. It tells Bob to:

      • Gather the screen name, target path, theme and port before writing a file
      • Scaffold non-interactively
      • Install with npm install --ignore-scripts
      • Patch esbuild/lib/main.js so that Vite falls back to esbuild-wasm on os400
      • Declare the Carbon theme before the component styles and wrap the app in <Theme>
      • Start the development server through a start-dev.sh launcher that resolves its environment before forking, rather than through nohup npm run dev &

      Each rule prevents a failure that occurred in earlier builds.

    1. In the Bob chat panel, switch the mode selector to Agent. Click + and choose Local Workspace (your ibmiflight400 folder) as the task context. copy & paste the following instruction. Press Enter to execute the task.

      Create a skill from the pasted text.

      Bob writes the skill file and confirms where it saved it. If Bob asks whether to save the skill globally or in the workspace, choose global, so that it is available from the library-list task in the next section.

    vi. Generating the React application

    With Node.js in place and the skill saved, the generation itself is a single prompt with an image attached. The image is a screenshot of the 5250 Create Order screen; the Premium Package's dds-primer-basics and rpg-primer-basics skills do the rest of the reading from the display file and the program.

    1. Save the screenshot of the Create Order screen to your local machine (right-click the image and save it).

      If you prefer your own capture, sign on to the 5250 terminal, start the application with GO FLGHT400/FRSMAIN and take a screenshot of the order entry screen.

    1. Switch the mode selector back to IBM i Developer.

      • Click + › New task in Library List so that the task is scoped to FLGHT400
      • Confirm in the Permissions menu that Documentation and Understand are enabled

    1. Drag the screenshot into the prompt field (or paste it from the clipboard), then copy & paste the following instruction. Press Enter to execute the task.

      Given this screenshot of the 5250 flight order screen from the application FLIGHT400 in @FLGHT400, build a single-page React 18 + Vite 4 app on IBM i (PASE) using @carbon/react ^1.x with the g100 dark theme that modernises the IBM i 5250 screen shown in the attached screenshot. Create the app in the IFS at $HOME/flight400-frontend-apps/create-order/. Use the g100 dark theme. All fields should have a list of values to select from. The dev server must run in the background using nohup ... & and write output to /tmp/vite-dev.log. Pin the Vite dev server to port 3001 if available.

      THE @ MENTION

      @FLGHT400 attaches the library to the task's context, which is how Bob knows where to find FRS001DF and FRS001 without being told their source files. Type the @ and pick the library from the list that appears, so that it is highlighted as a mention rather than left as plain text.

    1. Bob drafts a to-do list and pauses for approval. In the documented run, it activated the ibmi-react-vite skill together with dds-primer-basics (to parse FRS001DF.DSPF for the layout, field names and subfile windows) and rpg-primer-basics (to read FRS001.RPG for the pricing logic and field definitions), then listed the steps of the skill: scaffold, write package.json, install, patch esbuild, configure Vite and the theme, write the components and the launch scripts, and build.

      Click Approve todo tools for task, then approve the PASE command and IFS write requests as they appear. The npm install step is the long one; expect the whole task to take ten to fifteen minutes.

      TROUBLESHOOTING: THE BUILD FAILS

      Most failures trace back to a step of the skill being skipped. Unsupported platform: os400 ppc64 BE means the esbuild patch did not run; ask Bob to re-run node patch-esbuild.cjs and build again. A hang during npm install means --ignore-scripts was omitted. A page that renders in the white theme means the theme @use landed after the component styles. In each case, point Bob to the relevant section of the skill instead of describing the fix, since the skill already contains it.

    1. When the build completes, ask Bob to start the server:

      Please start the dev server for the app you just created.

      Bob runs the start-dev.sh launcher, which detaches the Vite server with nohup and records its process ID. It reports the PID and the port the server is listening on. If port 3001 was taken, Vite moves to the next free port and Bob tells you which; use that port in the tunnel below.

    vii. Opening the application from your laptop

    The development server listens on the partition, and the partition's public interface does not expose port 3001. An SSH tunnel carries the port to your laptop over the same connection Bob uses.

    1. In the Bob IDE, open a local terminal (Terminal → New Terminal) at the root of your workspace, where ssh_private_key.pem lives. Run the following, replacing <public-ip> with the Virtual machine 1 public IP address from your TechZone reservation, and leave the terminal open:

      ssh -i ssh_private_key.pem -N -L 3001:localhost:3001 ITZUSER@<public-ip>

      -N opens the tunnel without starting a remote shell, so the command appears to hang. The command is holding the tunnel open, which is expected. Press Ctrl+C to close it when you are finished.

    1. Open http://localhost:3001 in your browser. The Create Order screen renders as a Carbon page in the g100 dark theme, with the Flight Information and Ticket Order Information panels as tiles. The lookups become dropdowns and the class of service becomes a set of radio buttons. The function keys appear as a row of buttons along the bottom, with F10 – Make Reservation as the primary action.

      TROUBLESHOOTING: NOTHING SHOWING IN THE BROWSER

      Check three things in order. The tunnel terminal is still open and reported no error. The port in the tunnel matches the port Bob reported in the previous section; if Vite moved to another port, change both ends of the -L argument. And the server is still running: ask Bob "Is the dev server for the create-order app still running? Show the last lines of its log." The log is at /tmp/vite-create-order.log (the skill names it after the screen) or at /tmp/vite-dev.log.

    1. When you have finished exploring, ask Bob to stop the server:

      Stop the web service for FLIGHT400 on port 3001.

      Bob reads the recorded PID and ends the process. Close the tunnel with Ctrl+C in the terminal. A Node.js server left running would show up as a PASE job in the active-jobs list from Module 5, which is a useful check if you are unsure whether it stopped.

      SAMPLE DATA ONLY

      The generated application runs with sample data; its dropdowns are populated from what Bob read in the display file and the RPG program, and Make Reservation does not write an order. The natural next step is a REST layer that connects the page to the real business logic and to Db2 for i. FLIGHT400 already has the beginnings of one: the six ILE service programs that the Understand scan reported in Module 1 are its REST API layer, and the AGENTS member records how they must be compiled.

    viii. Key takeaways

    • A skill you author yourself works the same way as the Premium Package's own: a Markdown file with a description that tells Bob when to apply it, which Bob then combines with the platform skills (dds-primer-basics, rpg-primer-basics) that a task needs
    • Platform knowledge belongs in a skill. The esbuild patch, --ignore-scripts, the non-interactive scaffold and the detached launcher are recorded there and applied on each run
    • Bob can read a 5250 screen from its DDS and its RPG program and produce a React application styled with IBM Carbon that preserves the fields, lookups and function keys of the original
    • The application is built and served on the partition itself, in PASE, and reached from a laptop through an SSH tunnel; only the browser runs outside the IBM i
    • A generated front end on sample data is a starting point; connecting it to the application's REST layer and to Db2 for i is the modernization work that follows
    • Human review remains essential. A page that renders is a prototype; compare the generated fields and lookups with the display file before it is shown as finished work
