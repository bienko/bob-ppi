## **i. From single-program modernization to cross-stack change**

In the previous section, you modernized `FRS409`, the *Order Modification Confirmation Window*. Bob explained the program, converted it from fixed-format OPM RPG to free-format ILE RPG, compiled it and wrote a summary report.

Modernizing a single program is a meaningful first step, but real-world IBM i changes rarely stop at one source member. Adding a new business field, something as simple as *Total Flight Hours*, touches the physical file, the logical file, the RPG program and the display file. If any one of those layers is missed, the field does not appear on the screen, does not persist to the database or causes a runtime failure.

With the single-program modernization complete, this section adds a business field **end to end**.

Throughout this section, you will first give the *IBM i Developer* mode a set of standing rules for fixed-column source changes. You will then use IBM Bob to explore the *Flight Maintenance* screen and trace the existing `Mileage` field through every layer. A focused impact analysis follows, after which you will add a new *Total Flight Hours* field across four source members. Finally, you will compile all four objects in dependency order, validate the end-to-end field mapping and confirm the result on a live 5250 terminal.

!!! note "AI MATURITY CURVE"
    This module distributes control the way **Module 2 | Delegate** did. Each change arrives as a *proposed diff* that you approve explicitly, and each edit is insert-only, with the plan-first discipline applied at the granularity of individual source members. The standing rules you create at the start are the IBM i counterpart of the Bob Rules from **Module 3 | Tailor**: conventions that Bob applies in every task. A change reaches the LPAR only after you have read and approved it.

## **ii. Why this matters**

Cross-stack field changes are one of the most common, and most error-prone, activities in IBM i development.

!!! note ""
    Successfully extending a business field end to end requires more than editing one source member. Engineers must:

    - Understand how existing fields flow from physical file through logical file, RPG program and display file
    - Identify the minimum set of source members that must change
    - Preserve DDS column alignment, field naming conventions and indicator patterns
    - Update the RPG program's F-spec record length, I-spec byte mapping, `Z-ADD` screen-to-file operations, O-spec output and validation subroutines
    - Compile objects in the correct dependency order (physical file, then logical file, then display file, then program)
    - Verify the result visually on a live 5250 screen

| TASK | WITH: Manual Change | WITH: IBM Bob Premium Package for i |
| --- | --- | --- |
| Impact analysis | `DSPDBR`, `DSPPGMREF` and a careful read of every member that opens the file | A traced field path and the minimum change set, with follow-up programs listed separately |
| DDS and fixed-column RPG edits | Counting columns by hand, where a single mis-padded column means a compile failure | Insert-only diffs that copy the column positions of a model line, reviewed before they are saved |
| Standing conventions | Re-explained to every developer and in every ticket | Custom instructions on the mode, applied in every task |
| Build order and validation | An unwritten checklist | A build in dependency order, then a validation report against the live catalog and the DDS previewer |

## **iv. Creating standing rules for IBM i Developer mode**

In fixed-column source, small alignment mistakes have large consequences. An O-spec end position padded one column to the right compiles into the wrong byte offset, and a `COLHDG` keyword that belongs in a physical file is an error in a display file. The prompts in this module spell out those constraints, and Bob follows them, but a constraint stated only in a prompt has to be repeated by each developer in each prompt.

The Premium Package offers a better place for them: **custom instructions** on the mode itself. Rules written into the *IBM i Developer* mode's configuration are part of Bob's context in every task that runs in that mode, without being pasted into the chat. You will add the rules for planning and implementing fixed-column code changes now, before the first edit.

!!! info "THREE PLACES FOR STANDING GUIDANCE"
    You have now met three mechanisms that shape Bob's behavior before a prompt is read. **Custom instructions** on a mode travel with the mode and apply to every task that uses it. The **`AGENTS`** member written by `/init` travels with the library and records what Bob discovered about it. **Bob Rules** in a workspace's `.bob/rules/` folder, which you created during the previous course, travel with the project. Custom instructions on the mode describe how Bob should work. The `AGENTS` member records facts about the library. Workspace rules record facts about the project.

## **xiii. Key takeaways**

---

- IBM Bob can extend a business field **end to end** across physical files, logical files, RPG programs and display files, while preserving DDS column alignment, field naming conventions, indicator patterns and the existing OPM RPG style
- **Custom instructions** on the *IBM i Developer* mode turn the constraints of fixed-column editing into standing rules that apply in every task, so they no longer have to be repeated in every prompt
- **Impact analysis before implementation** is the most important step in the process. Bob traces the existing `Mileage` field through every layer, identifies the minimum source members that must change, specifies the build order and lists follow-up programs before any source is edited
- Cross-stack changes are best performed using **carefully sequenced prompts**, each focused on one layer (DDS, display file, RPG), with each proposed diff reviewed and approved before moving to the next
- **Insert-only** editing keeps the change safe: no existing DDS or RPG lines were modified, so the risk to existing function is low
- Objects must be compiled in **dependency order**: physical file, logical file, display file, program. Bob knows this order and executes it correctly, and still pauses for human approval
- Bob can **self-heal** minor compilation errors (such as the `FHRS` → `FFHRS` typo in the C-spec) by detecting the error, correcting the source and recompiling
- The **Validation Report** is the final checkpoint: Bob queries the live QSYS2 catalog, the DDS Previewer and the source to confirm that the field exists at every layer and that invalid keywords were excluded
- **Follow-up programs** (`FRS413`, `FRS001`, `FRS002` and `BFLGHT`) are identified and intentionally left out of scope. In a real project, each would need its own F-spec and I-spec update to match the new 236-byte record length
- Human review remains essential at every step. Verify the column positions, byte offsets and indicator numbers in each diff against the source before approving it
