    EXTENDING BUSINESS LOGIC ACROSS THE STACK

    i. From single-program modernization to cross-stack change

    In the previous section, you modernized FRS409, the Order Modification Confirmation Window. Bob explained the program, converted it from fixed-format OPM RPG to free-format ILE RPG, compiled it and wrote a summary report.

    Modernizing a single program is a meaningful first step, but real-world IBM i changes rarely stop at one source member. Adding a new business field, something as simple as Total Flight Hours, touches the physical file, the logical file, the RPG program and the display file. If any one of those layers is missed, the field does not appear on the screen, does not persist to the database or causes a runtime failure.

    With the single-program modernization complete, this section adds a business field end to end.

    Throughout the module ahead, you will first give the IBM i Developer mode a set of standing rules for fixed-column source changes. You will then use IBM Bob to explore the Flight Maintenance screen and trace the existing Mileage field through every layer. A focused impact analysis follows, after which you will add a new Total Flight Hours field across four source members. Finally, you will compile all four objects in dependency order, validate the end-to-end field mapping and confirm the result on a live 5250 terminal.

    ii. Why this matters

    Cross-stack field changes are one of the most common, and most error-prone, activities in IBM i development.

    Successfully extending a business field end to end requires more than editing one source member. Practitioners must:

    • Understand how existing fields flow from physical file through logical file, RPG program and display file
    • Identify the minimum set of source members that must change
    • Preserve DDS column alignment, field naming conventions and indicator patterns
    • Update the RPG program's F-spec record length, I-spec byte mapping, Z-ADD screen-to-file operations, O-spec output and validation subroutines
    • Compile objects in the correct dependency order (physical file, then logical file, then display file, then program)
    • Verify the result visually on a live 5250 screen

    ATTENTION: NON-DETERMINISTIC WORK AHEAD

    Bob's responses are non-deterministic, so the exact diffs, column positions, indicator numbers and compilation messages you see may differ from those shown here.

    IBM Bob is powered by generative AI and LLMs, and a defining trait of these systems is that they are non-deterministic — unlike the deterministic tools most IBM i developers are accustomed to. In practice, the same prompt can produce different DDS, RPG or display-file code from one run to the next.

    All this is to say: Your results ahead may vary. The key takeaway from this workflow is that you understand how to use Bob's impact analysis, review proposed diffs and approve compilation steps. Whether or not you arrive at the exact same column positions or indicator numbers is of less importance — Bob will produce a compilable, functionally correct result either way. The exact implementation details, however, may differ from those documented here.

    iv. Creating standing rules for IBM i Developer mode

    In fixed-column source, small alignment mistakes have large consequences. An O-spec end position padded one column to the right compiles into the wrong byte offset, and a COLHDG keyword that belongs in a physical file is an error in a display file. The prompts in this module spell out those constraints, and Bob follows them, but a constraint stated only in a prompt has to be repeated by each developer in each prompt.

    The IBM Bob Premium Package for i offers a better place for them: custom instructions on the mode itself. Rules written into the IBM i Developer mode's configuration are part of Bob's context in every task that runs in that mode, without being pasted into the chat. You will add the rules for planning and implementing fixed-column code changes now, before the first edit.

    THREE PLACES FOR STANDING GUIDANCE

    You have now met three mechanisms that shape Bob's behavior before a prompt is read.

    1. Custom instructions on a mode travel with the mode and apply to every task that uses it.
    2. The AGENTS member written by /init travels with the library and records what Bob discovered about it.
    3. Bob Rules in a workspace's .bob/rules/ folder, which you created during the previous course, travel with the project.

    Custom instructions on the mode describe how Bob should work. The AGENTS member records facts about the library. Workspace rules record facts about the project.

    1. Click the settings icon (the gear) at the top-right of the Bob panel. The Bob Settings tab opens in the editor area.

    1. Click Modes in the left sidebar of the settings tab. The table lists the built-in modes (Agent, Plan and Ask) together with the two modes the Premium Package contributes, IBM i Database and IBM i Developer, each marked with the Extension scope.

      Select IBM i Developer.

    1. The mode's detail page shows its description, its extension source (IBM i), its role definition and when to use it. Click the Edit mode (pencil) icon at the top-right of the page to open the mode editor, titled Edit IBM i Developer mode (IBM i).

    1. Scroll down through the Custom Instructions text area to the end of the existing Interaction Guidelines, and paste the following block beneath them:

      ## When a user asks to plan or implement code changes
- Make insert-only changes using apply_diff with surrounding context; do not use insert_content.
- When inserting, anchor the diff on the line ABOVE the insertion point and do not include trailing structural lines (DDS key "K ..." or record-format "R ..." lines) in the replacement - leave those lines untouched.
- When adding a fixed-form entry that mirrors an existing one (RPG I-spec, O-spec, or DDS field), copy the model line's EXACT column positions and change only the field name and value. Re-pad so numbers stay right-justified in their original columns and the data-type letter stays in its column. If the new field name is a different length than the model, adjust the padding so every downstream column is unchanged. Never eyeball the spacing.
- Preserve exact DDS column positions for field-definition entries (name, length, type). Keyword continuation lines like COLHDG only need to start after position 44 - do not fixate on their exact alignment.
- Preserve the existing OPM RPG fixed-column style.
- Do not add ALWNULL, do not use SQL ALTER TABLE, do not change the field to 5P 1.
- COLHDG belongs only in the physical file, never in the display file.
- Always show the diff and wait for my approval before saving; never compile until I say so.

      Click Save.

      READ THE RULES BEFORE YOU SAVE THEM

      Each line corresponds to a problem that came up in earlier runs of this change. The anchor above the insertion point rule keeps Bob from swallowing a DDS key line into its replacement; the copy the model line's exact columns rule keeps O-spec end positions right-justified; the never compile until I say so rule is the approval gate that the rest of this module depends on. Bob will apply them in every IBM i Developer task from now on.

    1. Close the settings tab. The prompts that follow still spell out the same constraints in full, so that the documented run can be reproduced from this page as written. In your own work, the standing rules let you shorten them considerably.

    xiii. Key takeaways

    • IBM Bob can extend a business field end to end across physical files, logical files, RPG programs and display files, while preserving DDS column alignment, field naming conventions, indicator patterns and the existing OPM RPG style
    • Custom instructions on the IBM i Developer mode turn the constraints of fixed-column editing into standing rules that apply in every task, so they no longer have to be repeated in every prompt
    • Impact analysis before implementation is the most important step in the process. Bob traces the existing Mileage field through every layer, identifies the minimum source members that must change, specifies the build order and lists follow-up programs before any source is edited
    • Cross-stack changes are best performed using carefully sequenced prompts, each focused on one layer (DDS, display file, RPG), with each proposed diff reviewed and approved before moving to the next
    • Insert-only editing keeps the change safe: no existing DDS or RPG lines were modified, so the risk to existing function is low
    • Objects must be compiled in dependency order: physical file, logical file, display file, program. Bob knows this order and executes it correctly, and still pauses for human approval
    • Bob can self-heal minor compilation errors (such as the FHRS → FFHRS typo in the C-spec) by detecting the error, correcting the source and recompiling
    • The Validation Report is the final checkpoint: Bob queries the live QSYS2 catalog, the DDS Previewer and the source to confirm that the field exists at every layer and that invalid keywords were excluded
    • Follow-up programs (FRS413, FRS001, FRS002 and BFLGHT) are identified and intentionally left out of scope. In a real project, each would need its own F-spec and I-spec update to match the new 236-byte record length
    • Human review remains essential at every step. Verify the column positions, byte offsets and indicator numbers in each diff against the source before approving it
