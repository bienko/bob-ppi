    MODULE 1 | ANALYZE

    FROM LEGACY IBM i TO LIVING DOCUMENTATION

    i. Where modernization begins

    In the previous Setup chapter, you provisioned an IBM i partition from IBM Technology Zone, installed the Premium Package for i and connected IBM Bob to the LPAR. The FLGHT400 library is restored and on your library list. At this point you have a running, production-style IBM i application in front of you and almost no working knowledge of what it does, how it fits together or which business rules it enforces.

    Understanding a legacy application is the first step in any modernization initiative. Before code can be modernized, extended or safely refactored, developers must establish confidence that the underlying business rules have been correctly identified, and that their understanding of the application matches what is actually running. With the environment in place, you can begin to study the application.

    Throughout this module, you will use IBM Bob to analyze FLIGHT400. You will browse the restored library in the Object Browser, write Bob's own context file for the library with the /init command, scan the application into the Understand Dashboard and query the dependency graph it builds. You will then extract business rules from a representative RPG program with the guided Business Rules Extraction workflow. Finally, you will generate a Markdown architecture overview of the whole application and append a Mermaid entity relationship diagram produced by the /erd command.

    AI MATURITY CURVE

    This module follows the pattern of the previous course. Building a durable, written understanding of an estate before changing it is the discipline you practiced there, and the artifacts you produce here (the AGENTS member, the Understand scan, the business-rules report, the architecture overview and the ERD) serve the same purpose as the persistent artifacts of Module 4 | Scale & Extend: understanding that is written down once and available to every later conversation. The subject is different, in that the Agentic Sidebar now works against a live IBM i LPAR.

    ii. Why this matters

    IBM i modernization projects often fail because critical business logic is misunderstood, or missed entirely, during migration.

    Successfully modernizing an IBM i application requires more than reading RPG source top to bottom. Engineers must:

    • Recognize the business rules encoded in decades of accumulated source
    • Understand the flows between programs, screens and database files
    • Identify which fields, files and members are affected by any given change
    • Preserve the naming conventions and patterns already in production
    • Produce documentation that survives beyond the individuals who built the original system
    TASK WITH: Manual Analysis WITH: IBM Bob Premium Package for i
    Application inventory and dependencies Hours of DSPPGMREF, DSPDBR and spreadsheets, repeated for every question One scan of the compiled objects, browsable in the Understand Dashboard and queried by Bob on demand
    Business rules for one program Days reading fixed-format RPG and the files it touches A business-language Markdown report with Mermaid diagrams from a guided workflow
    Architecture overview Weeks of interviews and hand-drawn diagrams Minutes of generation from the live library
    Entity relationship diagram Manual reconstruction from DDS key specifications /erd against the live catalog
    Project conventions for the next engineer Passed along by word of mouth An AGENTS member that Bob reads at the start of every task

    Doing this manually across a codebase with dozens of programs, thousands of DDS members and no formal architecture document is a common reason that modest modernization estimates turn into multi-year projects. Bob shortens that discovery phase to minutes, provided you drive it deliberately, review its output and capture what it finds in a durable form.

    iii. Analyzing FLIGHT400 with IBM Bob

    The first stage of analysis is making the FLGHT400 library visible to Bob and giving Bob a persistent picture of what is inside it.

    Using the Object Browser, the Understand Dashboard and the IBM i Developer mode, Bob can:

    • Enumerate every program, source member, database file and menu in the library
    • Record the library's source layout, compile conventions and quirks in an AGENTS member that every later task reads
    • Map every object and the dependencies between them from the compiled objects alone
    • Read and reason about individual source members line by line
    • Extract business rules from RPG source into plain-language reports
    • Introspect the QSYS2 catalog to produce architecture diagrams and ERDs

    ATTENTION: NON-DETERMINISTIC WORK AHEAD

    Bob's responses are non-deterministic, so the exact prompts, tool approvals and even section headings you see may differ from those shown here.

    IBM Bob is powered by generative AI and LLMs, and a defining trait of these systems is that they are non-deterministic — unlike the deterministic tools most IBM i developers are accustomed to. In practice, the same prompt can produce different Markdown, diagrams or field summaries from one run to the next.

    All this is to say: Your results ahead may vary. The key takeaway from these workflows is that you understand how to use Bob's modes, workflows and slash commands effectively. Whether or not you arrive at the exact same architecture document is of less importance — Bob will produce more or less what you asked for either way. The exact implementation and structure it uses to arrive at that result, however, may differ from the steps documented here.

    ABOUT THE SCREENSHOTS IN THIS MODULE

    Some of the screenshots in the Understand and /init sections were captured on a shared partition where each participant worked in a numbered copy of the library (FLGHT401, FLGHT402 and so on) with a numbered metadata library (BOBLIB01).     iv. Setting up the object browser

    Before Bob can help you reason about FLIGHT400, add an Object Browser filter that points at your FLGHT400 library so its contents are visible in the IBM i sidebar.

    1. In the Object Browser panel of the IBM i sidebar, click + Create new filter… to open the filter creation form.

    1. Fill in the filter fields:

      • Libraries: FLGHT400
      • Object types: *ALL

      Leaving Object types at its default (*SRCPF) would hide programs, database files, menus and display files, which are the objects you need to see. Setting it to *ALL gives Bob visibility into every object type in the library.

      Press Save settings.

    1. The Object Browser now shows every object in the library: programs, source files, database files, display files and menus. Expand the qrpgsrc source file and open one or two of its members to see the fixed-format style you will be modernizing in the next module.

      Then expand qddssrcd and open frs001df, the DDS for the Create Order screen. Click Preview All on the first line of the editor to render the green-screen layout as it would appear on a 5250 terminal.

      THE DDS PREVIEWER

      The previewer draws the display file's record formats on a 24×80 grid, with input fields underlined and function keys listed along the bottom. You will use the same preview in Module 2 to confirm where a new field lands on the Flight Maintenance screen (frs021df), so preview that member now as well.

    1. Back in the Object Browser, click FRS000.PGM (the flight reservation logon program) and open its Detail view with a right-click › Detail. The creation date reads 1997.

      The program has been in production for close to three decades, and the developers who wrote it are no longer available. The rest of this module documents what they knew.

    v. Initializing Bob's context with /init

    An AGENTS member gives Bob persistent, project-specific context about a codebase: its source file layout, compile conventions, naming patterns and the pitfalls that are easy to miss. Bob reads this member at the start of every task, so it already knows how the library is structured, which source files hold which members and where the known problems are. The Premium Package for i generates it with the /init slash command, which works in library-list (QSYS), IFS and local-workspace tasks alike.

    1. /init writes its output into the current library of your connection, so that library must be set before you run it. In the IBM i sidebar, expand User Library List, right-click FLGHT400 and select Set as Current Library.

      A CURRENT LIBRARY IS REQUIRED

      Without a current library set, /init prompts you to set one and stops. IBM-supplied system libraries such as QGPL and QTEMP are refused: if your connection defaulted to QGPL as its current library, Bob will ask you to switch to an application library before continuing.

    1. Open the Bob chat panel. Click the mode selector at the bottom and choose IBM i Developer. Then click the + button at the top-right of the panel and choose New task in Library List, which scopes the task to your library list (QGPL, QTEMP, FLGHT400).

    1. Type /init into the prompt field. The command list above the field narrows to the /init entry; select it so that the command is highlighted, then press Enter.

      Bob scans the library (source files, member types, service programs, IWS web services, naming conventions and database objects), creates a QBOBSRC source physical file in FLGHT400 if one does not exist and writes an AGENTS member into it in Markdown format. Approve the tool requests as they appear; the scan takes a minute or two.

    1. In the Object Browser, expand FLGHT400 › QBOBSRC and click the AGENTS member (shown as agents.md) to open it.

      The member contains IBM i-specific facts discovered directly from the source. In the documented run, Bob recorded, among other things:

      • Which source file holds the IWS REST service programs (EVFTEMPF01) and why they must be compiled with CRTSQLRPGI instead of CRTBNDRPG
      • That the *Z logical files (AGENTSZ, FLIGHTSZ and the rest) exist only for legacy Query/400 and should not be used as access paths in new code
      • That function key hex constants (F03=X'33', ENTER=X'F1') are declared per program with no shared copybook
      • That the display file FRS411DF must be compiled with DEFER(*NO), a non-default parameter

      From this point on, every new task in this library reads FLGHT400/QBOBSRC/AGENTS before it does anything else. The rules also load into the running session immediately, so there is no need to reconnect.

      THE SAME COMMAND IN OTHER WORKSPACES

      In an IFS task, /init writes an AGENTS.md stream file into the working directory; in a local workspace it writes a local AGENTS.md. The content is tailored to whichever workspace type Bob detects. If the member already exists, a second /init updates it and keeps any manual edits you added.

    vi. Scanning the application with the Understand Dashboard

    The Understand Dashboard scans an IBM i application library and builds a dependency graph of every program, file, service program, menu and command in it, with no source reading on your part. It works from the compiled objects on the system and stores what it finds in a metadata library of your choosing. Use it to answer "what is this application made of?" and "what breaks if I change X?" before any code is changed.

    ONE SCAN, SHARED BY THE TEAM

    The metadata library can be shared across a development team, so that everyone benefits from a single scan — provided each developer is granted authority to it. On this partition you are the only user, so you will create a dedicated BOBLIB library for the component. The dashboard's Access Control tab is where a team would audit and grant that authority later.

    1. Open the Command Palette (Cmd+Shift+P / Ctrl+Shift+P) and run Get Started with Understand.

      A short walkthrough opens. Its first step, Connect to IBM i, is already satisfied by your connection. The second, Install the Understand component, explains that Understand keeps its results in one IBM i library. Click Open the Understand Dashboard.

    1. The dashboard opens on its Overview tab, with an Understand component card at the top.

      • If the card asks for an install library, enter BOBLIB
      • Click Install Understand and wait for the card to report the component as Installed

      The install creates the BOBLIB library and the Db2 objects the scanner writes to. It takes under a minute.

      CHOOSE A DEDICATED LIBRARY

      Use a library that does not already exist as a user library, and restrict its access to authorized users. The scanned metadata describes every object in the application, so a user with authority to BOBLIB can see data about objects they have no direct authority to.

    1. Switch to the Applications tab and click New application. An application is an ordered list of related libraries; for FLIGHT400 it is a single library. Fill in the form:

      • Display name: FLIGHT400
      • Description: Flight reservation application discovery
      • Libraries: pick FLGHT400 from the suggestions (or type it) and click Add

      Then click Add application.

      LIBRARIES ARE SCANNED IN THE ORDER ADDED

      System libraries (QSYS, QSYS2, SYSIBM and the like) are excluded automatically. Add the library that holds the compiled objects (FLGHT400), which here is also the library that holds the source. Source physical files are not listed as objects in the scan.

    1. Click Scan next to the new application. Progress appears in the lower part of the dashboard, and the scan runs in its own SQL jobs so you can keep using the other tabs while it works. It completes in 30 to 60 seconds, after which the application's status reads Scanned.

      Return to the Overview tab: the component card now reads Installed with BOBLIB as its install library, and the Applications table lists FLIGHT400 as Active and Scanned.

    1. Open the Insights tab with FLIGHT400 selected. The top of the tab summarizes the object and dependency counts for the application; use it to answer the questions below.

      QUESTION WHERE TO LOOK
      How many programs are there? Objects summary — the PGM row
      How many are OPM (legacy RPG and CL) versus ILE? Objects summary — the OPM / ILE split
      How many physical files (tables)? Objects summary — the FILE / PF row
      Are there any service programs? Objects summary — the SRVPGM row
      Is there any dynamic SQL? Dynamic SQL risks

      In the documented run, FLGHT400 scanned to roughly 42 programs (39 OPM and 3 ILE), 15 physical files, 6 ILE service programs (the REST API layer) and no objects using dynamic SQL. Those numbers confirm what the 1997 timestamp suggested: a classic OPM RPG application with a modern REST layer added on top.

    1. Scroll down to Most referenced objects. The list ranks objects by inbound dependencies — the number of other objects that use them — which shows where a change would have the widest effect.

      In the documented run, the physical files ORDERS (17 references), CUSTOMERS (13), TOCITY (11) and FRCITY (11) led the list. Database files dominate the top of the ranking, which tells you that the application's core dependencies run through its data rather than through program-to-program calls. Note how the dependency chart above the list breaks the relationships down by type: file opens, program calls, bound modules, data area references and command processing programs.

    1. Open the Objects tab, search for FRS021 and select the program. The panel shows its outbound dependencies (the files and programs it uses) and its inbound dependencies (what uses it), together with the related file information and a Last Used column.

      Note this view. FRS021 is the Flight Maintenance program you will extend in Module 2, and the files listed under its outbound dependencies are the ones that change will touch.

    1. With the scan in place, Bob gains six Understand tools and three Understand skills in the IBM i Developer and IBM i Database modes. Whether it may use them in a given task is controlled by the Understand permission group, so enable it before asking.

      In the Bob chat panel, click + › New task in Library List and confirm that IBM i Developer is the active mode. Then open the Permissions menu beside the mode selector and switch on both Documentation and Understand.

      ENABLE BOTH PERMISSIONS FOR EVERY TASK THAT FOLLOWS

      Documentation lets Bob retrieve passages from the official IBM i documentation (a RAG-based tool) and Understand lets it query the scan. Both apply across the remaining modules — documentation, refactoring, database tuning and testing all benefit — so check the Permissions menu each time you start a new task.

    1. Copy and paste the following prompt into the Bob chat and send it:

      What are the high-level functional areas of FLGHT400?

      Bob activates the understand-app-overview skill and answers from the scan data: the functional areas of the application, the key programs within each and an architecture diagram, produced from the scan data alone. Compare the response with what you saw in the Insights tab; the two should agree on which files sit at the center of the application.

    vii. Extracting business rules from an RPG program

    The Business Rules Extraction workflow is one of several guided workflows shipped with the Premium Package for i. It walks Bob through reading an RPG source member, discovering its dependencies, cataloguing its rules and decision logic, and producing a business-friendly Markdown report with Mermaid diagrams. For FLIGHT400, you will run it against FRS401.RPGLE, the Agent Selection Window subprogram and a good representative of the mid-sized programs that dominate the codebase.

    SEQUENCING THE WORKFLOW

    The Business Rules Extraction workflow is guided: Bob prompts you at each step to select a library, source file and member. You answer those prompts, and Bob does the reading, dependency discovery, rule extraction and report writing on its own.

    1. Click the workflow icon (the play button at the top-right of the Bob panel) and choose Run Workflow in Library List. This scopes the workflow to QGPL, QTEMP, FLGHT400, matching what is on your library list.

    1. The Bob workflows panel opens and lists the workflows available in this mode: RPG Modernization, SQL Index Strategy Advisor, RPGUnit Test Plan Creation, RPGUnit Test Suite Implementation and Business Rules Extraction. Four of the five appear later in this lab.

      Click Start on Business Rules Extraction.

    1. The workflow opens with a Welcome screen explaining what it does: it reads your RPG source, extracts business rules, generates a Markdown report and produces Mermaid diagrams.

      Click Get Started to continue.

    1. On the Select Library step, choose FLGHT400 from the dropdown, then press Continue.

    1. On the Select Source File step, choose QRPGLESRC, the source file containing the ILE RPG members. Press Continue.

    1. On the Select Member step, choose FRS401.RPGLE, the Agent Selection Window program. Click Analyze Member.

      Bob spawns a subagent that reads FRS401, walks its dependencies (AGENTSL.LF, FRS401DF.DSPF and AGENTS.PF) and starts extracting business rules across the mainline and each subroutine.

    1. When Bob finishes extracting rules and generating diagrams, it prompts for a save location. Accept the default IFS path (for example /home/ITZUSER/flght400/docs/business-rules/FRS401-2026-08-06T21-43-45.md) and press Continue to save the report.

    1. Once saved, Bob shows a Report Saved panel with the full path and an Open File button. Click Open File to view the generated report.

    1. Take a few moments to review the generated report. It includes:

      • An Executive Summary describing FRS401 in plain business language — "reusable agent lookup and selection component", "pop-up window within the broader flight or agency management application"
      • A Detailed Business Rules section broken down by capability: alphabetical browsing, incremental name search, single-agent selection, input validation and clean message handling
      • Mermaid diagrams showing process flows and decision trees
      • Categorized rules with domain, description and priority

      The report is a durable artifact: an RPG program that previously took an IBM i developer hours to explain is now documented in language a business analyst can read.

    viii. Generating an architecture overview

    The business rules report covers a single program in depth. Next you will have Bob document the entire application. Ask Bob directly for an architecture overview in Markdown, and it will introspect the full library, catalogue the programs and produce a structured document you can keep on the LPAR alongside the code it describes.

    1. In the Bob chat panel, click + › New task in Library List and confirm that the Documentation and Understand permissions are enabled. Then paste the following request:

      Generate a comprehensive architecture overview of the FLGHT400 application in QSYS in Markdown format. Include a high-level description, the main program flows, key programs and their roles, a Mermaid architecture diagram, and a summary of the database tables used.

      Send the prompt.

      THE SCAN LOWERS THE COST OF THIS PROMPT

      This is the most expensive prompt in the module. With the Understand scan available, Bob can take the program inventory and the call relationships from metadata and reserve its source reads for the programs whose roles it needs to describe, which both shortens the run and reduces the Bobcoins it consumes.

    1. Bob builds a Todo List covering the discovery work (cataloguing programs, database files and display files, analyzing call flows and writing the overview) and pauses for your approval before running any tools.

      Review the proposed plan to ensure it aligns with what you asked for. Once you are satisfied, click Approve todo tools for task to let Bob proceed through the full list without re-prompting on every step.

    1. When Bob finishes, it displays the completed architecture overview inline in the chat and writes it to /home/FLGHT400_ARCHITECTURE.md on the LPAR.

      In the documented run, the overview covered seven sections:

      SECTION CONTENT
      High-Level Description FLIGHT400 as a full-lifecycle airline flight reservation system
      Application Architecture Diagram Mermaid flowchart TD covering menus, programs, lookup windows and database
      Menu Structure FRSMAIN, FRSMANT, FRSREPT and their child programs
      Program Catalogue Programs grouped by category: Session and Dispatch, Reservations, Maintenance, Lookup Windows, CL and Utilities
      Documented Call Flows New reservation, update, display, delete and fax, agent logon and the maintenance paths
      Database Summary Physical files, logical files and an ER summary anchored on ORDERS
      Modernization Status Which programs have already been converted to ILE free-format and which remain OPM-only

    ix. Adding an entity relationship diagram

    The architecture overview describes what programs exist and how they call each other. The last piece missing is how the data is shaped: the physical and logical files, their primary keys and the relationships between them. The Premium Package for i ships a /erd slash command that introspects the QSYS2 catalog and produces a Mermaid entity relationship diagram, which you will append directly to the architecture document.

    1. In the same Bob chat, type the following as your next prompt:

      /erd FLGHT400 add this to FLGHT400_ARCHITECTURE.md

      Send it. Bob runs the ERD generator against the FLGHT400 catalog, discovers the primary keys and relationships across AGENTS, CUSTOMERS, FLIGHTS, ORDERS, FNEXTO, FCITY/TCITY and FNAME/LNAME, then appends the resulting Mermaid ERD to the architecture document on the LPAR.

    1. In the IFS Browser, locate FLGHT400_ARCHITECTURE.md at /home/FLGHT400_ARCHITECTURE.md and open it. Use the Preview button in the editor toolbar to render the Markdown side by side with the source.

    1. Review the completed document. Alongside the architecture sections you saw in the chat, you should now see:

      • A Source File Inventory with QRPGSRC, QRPGLESRC, QCLPSRC, QDDSSRCF, QDDSSRCD and QMNUSRC
      • Notes on primary keys and FK constraints, defined by DDS K keywords rather than SQL DDL — a common IBM i pattern that Bob has correctly identified
      • An ERD Relationships Modelled section with the Mermaid diagram: ORDERS at the center, joined out to AGENTS, CUSTOMERS and FLIGHTS, with FNEXTO as the sequence generator and FCITY/TCITY/FNAME/LNAME as reference tables

      This document is the reference you will use when planning changes in Module 2 and when answering "what talks to what" questions during operations in Module 5.

      OPTIONAL: AN EDITABLE DRAW.IO DIAGRAM

      If you have token budget to spare, install the third-party Draw.io Integration extension from the Extensions view and send the following prompt in a new IBM i Developer task scoped to the library list:

      Analyze the FLGHT400 application from the library list and generate a draw.io architecture diagram showing the main programs, menus, and database files. Save the file as FLGHT400-architecture.drawio in $HOME/docs/ on IBM i.

      In the IFS Browser, navigate to /home/ITZUSER/docs/ and click the .drawio file: the extension renders the diagram directly in the editor, where you can rearrange it and refine it with follow-up prompts.

    x. Key takeaways

    • IBM Bob can analyze legacy IBM i applications and produce durable documentation without requiring years of RPG, DDS or CL expertise
    • Analysis work is best performed in IBM i Developer mode with the library list as the task scope, giving Bob visibility into every object it needs to reason about
    • /init writes an AGENTS member into QBOBSRC of the current library; every later task reads it first, so conventions and pitfalls are recorded once and no longer need repeating in each prompt
    • The Understand Dashboard scans the compiled objects of a library into a metadata library and maps every dependency between them; the Insights tab ranks the objects whose change carries the most risk
    • With the Understand and Documentation permissions enabled, Bob answers structural questions from scan data and the IBM i documentation rather than by re-reading source, which is faster and cheaper in Bobcoins
    • The Business Rules Extraction workflow produces deep, business-language reports on individual programs, which suits the mid-sized RPG programs that carry most of the business logic in an IBM i codebase
    • A direct chat prompt produces a wide architecture overview across the whole library, and the /erd slash command appends a Mermaid entity relationship diagram from the live catalog
    • Always review Bob's proposed Todo List before approving; it is cheaper to correct an error in the plan than after the tools have run
    • Human review remains essential at every step. Bob writes fluently whether or not it has read the right members, so review the generated document against the codebase before relying on it
